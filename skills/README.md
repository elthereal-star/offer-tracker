# skills/ · Offer Tracker 领域知识单元

这套目录把散落的项目文档，改造成**可被 Code Agent 直接消费的模块化业务知识单元**。

传统项目文档的问题不是写得少，而是写得"不可执行"：一份 3000 行的 `README.md` 里既有环境搭建、又有业务规则、又有踩坑记录，Agent 每次都得整份读完才能确认一件事；规则一旦分散在多个文档里，就会出现互相矛盾、没人知道哪份是真相源的情况。

这里的做法是把知识按**领域**切分，每个单元只回答一类问题，并且都指向真实代码位置。

## 目录约定

```
skills/
└── <skill-name>/
    ├── SKILL.md              # 入口：这层管什么、使用顺序、必守约束
    ├── agents/openai.yaml    # 宿主 Agent 的展示元信息与调用策略
    └── references/           # 分主题的细节文档，按需读取
```

- `SKILL.md` 必须包含 YAML frontmatter 的 `name` 与 `description`。`description` 写的是**触发条件**，不是内容摘要 —— Agent 靠它决定要不要读这个技能。
- `references/` 下的文件各自独立成篇，只回答一个问题。
- 所有结论都要能落到具体类、具体表、具体配置项上。**不允许出现"某处实现了某某机制"这种无法验证的表述。**

## 技能清单

| 技能 | 回答什么问题 |
|---|---|
| `ot-repo-map` | 这段逻辑在哪个模块？当前 profile 启用的是哪一套实现？配置项的真相源在哪？ |
| `ot-ai-interview-domain` | 面试会话的状态怎么流转？作答/评分/追问/收尾各自的守卫条件是什么？ |
| `ot-ai-runtime` | 重复的 AI 调用怎么折叠？什么情况会重试？锁和 fencing 令牌怎么配合？ |
| `ot-async-tasks` | 异步任务怎么投递、怎么消费、失败了怎么办？ |
| `ot-realtime-transport` | 实时事件怎么保证不丢不重不乱序？ |
| `ot-auth-and-isolation` | 用户身份从哪来？资源归属怎么约束？重复提交怎么防？ |

## 维护约定

1. **改代码必须同步改这里。** 尤其是 profile 归属、Redis key、single-flight key 组成这三类信息 —— 它们错了会直接误导后续修改。
2. 新增一节之前先确认它不属于已有技能，避免出现两份互相矛盾的说明。
3. 迁移脚本只增不改：已发布的 `V1`–`V19` 不允许回改，只能追加新版本号。
4. 这里写的是**当前实现的真相**，不是规划。尚未落地的设计写进 `docs/adr/`，不要混进来。
